# Codex adapter

Codex reads `AGENTS.md` natively, so the entrypoint needs no bridge. What it
does not share with the neutral core is a skills directory, a role format, and
an MCP configuration format. This directory holds the manifest, the mapping,
and the configuration head that close those three gaps. The files they
produce are generated by `scripts/sync-harness.py` and tracked in git, so a
clone needs no step between clone and session.

## Getting started on this harness

1. Clone the workbench and run the wiring check from its root:

   ```bash
   python3 scripts/check-harness.py
   ```

   `0 failure(s)` means the skills symlink is in place and every generated
   file matches its source. On Windows, clone with
   `git clone -c core.symlinks=true` first, and never use a zip download,
   which flattens a symlink into a text file.

2. Optional: install the plugin that carries code and design work. The
   workbench routes that work to `superpowers` in `AGENTS.md` under "How work
   runs". It is on the official Codex plugin marketplace: run `/plugins` in a
   session and install it from there (the plugin's own README, read
   2026-09-12, gives this path for Codex CLI). Its subagent dispatch uses the
   multi-agent tools, which the plugin's Codex reference,
   `skills/using-superpowers/references/codex-tools.md` in the plugin's own
   tree, says to enable with `[features] multi_agent = true` in
   `~/.codex/config.toml`; the configuration reference lists that feature as
   on by default (`https://learn.chatgpt.com/docs/config-file/config-reference`,
   retrieved 2026-09-12), so the line is a safeguard and not a requirement.
   Skip this step if the owner does not build software here.

3. Start a session at the workbench root and trust the project:

   ```bash
   codex
   ```

   "Codex loads project-scoped config files only when you trust the project"
   (`https://learn.chatgpt.com/docs/config-file/config-reference`, retrieved
   2026-09-12). Trust is recorded as `projects.<path>.trust_level = "trusted"`
   in the user-level configuration (same page and date). How the harness asks
   for it is not on that page; if no prompt appears, write the key by hand.
   Until the project is trusted, `.codex/config.toml` and `.codex/agents/`
   are not read.

4. Confirm the surfaces loaded. `/skills` lists the twelve skills, or type `$`
   to mention one ("In Codex CLI or the IDE extension, run `/skills` or type
   `$` to mention a skill", `https://learn.chatgpt.com/docs/build-skills`,
   retrieved 2026-09-12). The documentation retrieved on 2026-09-12 names no
   command that lists custom agents; a dispatch that names one by its `name`
   is the test.

5. Paste `prompts/setup.md` into the session. It walks the specialisation
   pass and ends by running the checks above again.

## What this adapter declares

`wiring.json` beside this file declares one symlink, one generated role
directory, and one generated configuration file.

| Path | What it is | Source | Retrieved |
|---|---|---|---|
| `.agents/skills` | Symlink to `skills/`. Codex scans `$REPO_ROOT/.agents/skills`, "the topmost root folder when you launch Codex inside a Git repository", and "supports symlinked skill folders and follows the symlink target when scanning these locations" | `https://learn.chatgpt.com/docs/build-skills` | 2026-09-12 |
| `.codex/agents/<role>.toml` | One generated file per `agents/*.md`. | `.codex/config.toml` | Generated: the head in `config.toml` beside this file, then one `[mcp_servers.<name>]` table per server in `.mcp.json`. Project-scoped configuration lives at `.codex/config.toml (trusted projects only)` | `https://learn.chatgpt.com/docs/extend/mcp` | 2026-09-12 |

### How a role file is generated

`developer_instructions` is the role's body, verbatim. When the role's
frontmatter has a `skills:` line, the body is preceded by one sentence that
names each `skills/<name>/SKILL.md` to read first. That is the `reference`
mechanism every adapter uses for the page schema, applied to skills. The
generator does not emit `skills.config`, because the documentation retrieved
on 2026-09-12 names the key and does not detail its schema.

`roles.json` beside this file maps roles to extra keys. `defaults` applies to
every role; an entry under `roles` applies to one and overrides `defaults`.
Every key is copied verbatim as a top-level TOML value, strings and booleans
only. It ships empty. A model identifier belongs here and nowhere in the
neutral core:

```json
{
  "defaults": {"model_reasoning_effort": "medium"},
  "roles": {"research-editor": {"model": "<a model your Codex accepts>"}}
}
```

After any edit to `agents/` or to this mapping:

```bash
python3 scripts/sync-harness.py
```

`scripts/check-harness.py` fails until the generated files match.

### How the MCP block is generated

`.mcp.json` at the workbench root is the one source of MCP servers. The
generator renders two shapes into `[mcp_servers.<name>]` tables and refuses
everything else by name, because a server the two harnesses read differently
is a server that works on one and silently not the other:

- A local server: `command`, `args`, and `env` become `command`, `args`, and
  `[mcp_servers.<name>.env]`. A value containing `${` is refused, because the
  target format performs no expansion.
- A remote server: `type: "http"` or `"sse"` with `url` becomes `url`. A
  header of exactly `Authorization: "Bearer ${NAME}"` becomes
  `bearer_token_env_var = "NAME"`. Any other header is refused.

The documented shapes are `command`, `args`, `env` for a local server and
`url` with `bearer_token_env_var` for a remote one
(`https://learn.chatgpt.com/docs/extend/mcp`, retrieved 2026-09-12).

`config.toml` beside this file is the hand-edited head of the generated file.
Edit it, never `.codex/config.toml`. It ships as comments only.

## Keys a project-scoped configuration cannot set

"Project-scoped config can't override machine-local provider, auth, host-owned
app request metadata, notification, configuration profile selection, or
telemetry routing keys." The ignored keys include `openai_base_url`,
`model_provider`, `model_providers`, `notify`, `profile` and `profiles`
(`https://learn.chatgpt.com/docs/config-file/config-reference`, retrieved
2026-09-12). A self-hosted run that changes only `.codex/config.toml` therefore
changes nothing; those keys belong in `~/.codex/config.toml`.

`agents.enabled` defaults to `true` (same page), so custom agents need no
feature flag of their own.

## Permissions

The template ships no permission rules. A custom agent inherits the session's
sandbox unless its file sets `sandbox_mode`, and this adapter's generator
emits that key only from `roles.json` ("Subagents inherit your current sandbox
policy", `https://learn.chatgpt.com/docs/agent-configuration/subagents`,
retrieved 2026-09-11).

## The entrypoint and the size cap

Codex reads `AGENTS.override.md` if it exists, otherwise `AGENTS.md`, from the
project root down to the working directory, and "skips empty files and stops
adding files once the combined size reaches the limit defined by
`project_doc_max_bytes` (32 KiB by default)"
(`https://learn.chatgpt.com/docs/agent-configuration/agents-md`, retrieved
2026-09-12). `scripts/check-harness.py` fails when the root `AGENTS.md` alone
exceeds that cap.

## The page schema arrives by reference

Same as every adapter: the routing row in `AGENTS.md` names
`central-context/AGENTS.md`, and each wiki skill names it as a required read.
Nothing in this adapter imports it. Schema column: `reference`.

## Model

Whatever `~/.codex/config.toml` selects. This adapter's `roles.json` may pin a
role to a model the harness accepts; it ships with none. `scripts/check-roles.py`
does not read the mapping, so a value here is checked only by the harness.

## Wiring check

`python3 scripts/check-harness.py` ran clean on this adapter's symlink and its
seven generated files on 2026-09-12, on the tree this file was committed in.
That proves the wiring, not the behaviour below.

## Removing the adapter

```bash
git rm .agents/skills
git rm -r .codex adapters/codex
```

`scripts/check-harness.py` then has no manifest for this harness and checks
nothing for it. `scripts/sync-harness.py --check` reports nothing to generate.
